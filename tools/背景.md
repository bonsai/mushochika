# 背景

## 1. 問題設定

AIによって、仕事の構成要素そのものが変化している。

従来は、

```text
職種
 ↓
仕事内容
 ↓
必要スキル
 ↓
経験年数
 ↓
採用
```

という形で人材を定義してきた。

しかしAI時代には、仕事を構成するTask、Knowledge、Skill、Tool、Agent、Workflow、Evidenceを分解して扱う必要がある。

したがって、求人だけではなく、**仕事そのものを構造化すること**が問題になる。

## 2. 社会的背景と数字

McKinseyは、生成AIを含む既存技術によって、現在の仕事時間の60〜70%が理論上自動化可能になり得ると推計している。

これは「仕事の60〜70%が消滅する」という意味ではなく、仕事を構成する活動の再設計が大きな論点になることを示している。

また、World Economic ForumのFuture of Jobs Report 2025では、2030年までに約1.7億の新しい仕事が生まれ、約9200万の仕事が置き換わり、差し引き約7800万の純増が予測されている。同時に、現在必要とされるスキルの約40%が変化すると企業が見込んでいる。

つまり、問題は単なる「AI人材不足」ではない。

```text
AI技術の進歩
 ↓
仕事の活動が変わる
 ↓
仕事の構造が変わる
 ↓
必要なSkillが変わる
 ↓
職種の定義が変わる
 ↓
求人・採用・教育・評価も変わる
```

## 3. Vibe Codingの登場

AIによるコード生成によって、開発の速度と方法も変化している。

GitHubが公表した95人のプロ開発者を対象とする実験では、GitHub Copilot利用者は同一課題を利用しない場合より55%速く完了した。また、課題の完了率は78%対70%だった。

ここから重要なのは、単純なコード生成能力ではない。

```text
Problem
 ↓
AIとの対話
 ↓
Code Generation
 ↓
Execution
 ↓
Test
 ↓
Failure
 ↓
Diagnosis
 ↓
Correction
 ↓
Integration
 ↓
Evidence
```

AIを開発ループの中に組み込み、生成・実行・失敗・修正・検証を反復する能力を、ここではVibe Codingとして捉える。

したがって、Vibe Codingは「AIにコードを書かせる技術」ではなく、**AIを含む開発ループを運用する技能**として定義する。

## 4. Agentへの展開

コード生成の次に起きるのは、仕事そのもののAgent化である。

```text
Human
 ↓
AI Assistant
 ↓
Agent
 ↓
Tool
 ↓
Workflow
 ↓
Execution
 ↓
Evidence
```

Agentは単なるLLMとの会話ではない。

```text
Agent = Intent + State + Decision + Tool + Workflow + Evidence
```

という実行主体として考える。

McKinseyは、現在の技術水準でもAgentが米国の仕事時間の44%に相当する活動を実行できる可能性を示している。

したがって、重要になる能力は「Agentを呼び出せること」ではなく、**仕事をAgentが実行可能な構造へ分解・設計できること**である。

## 5. Ontologyが必要になる理由

仕事をAgent化するには、まず「何が仕事なのか」を定義しなければならない。

例えば「採用を支援する」という要求だけではAgentは設計できない。

```text
Job
 ├─ Role
 ├─ Task
 ├─ Skill
 ├─ Knowledge
 ├─ Tool
 ├─ Qualification
 ├─ Constraint
 ├─ Evidence
 └─ Outcome
```

さらに概念間の関係を定義する。

```text
Job
 ↓ requires
Skill

Skill
 ↓ demonstratedBy
Evidence

Task
 ↓ performedBy
Agent

Agent
 ↓ uses
Tool

Task
 ↓ produces
Outcome
```

つまりOntologyは、AIに何をさせるか以前に、**対象となる世界をどう切り分け、何と何を関係付けるかを決める設計**である。

## 6. 三つの能力の接続

Vibe Coding、Agent Construction、Ontology Designは別々の技能ではなく、一つの開発循環として接続できる。

```text
Ontology
 ↓
Intent
 ↓
Agent
 ↓
Tool
 ↓
Workflow
 ↓
Vibe Coding
 ↓
Repository
 ↓
Evidence
 ↓
Outcome
```

したがって、新しい職能は、単なる「AIエンジニア」より広い。

> **意味を定義し、それをIntentとして表現し、Agentとして実行可能にし、AIとともに実装し、Evidenceによって検証する能力。**

## 7. 求人・人材評価への帰結

従来の求人評価は、経験年数、使用言語、資格、学歴などの属性に依存しやすい。

しかしAI時代には、実際に何をできるのかをEvidenceで評価する方が重要になる。

```text
従来
経験年数
資格
言語
職歴
   ↓
人材評価
```

から、

```text
新しい評価
Problem定義
Issue
Ontology / Schema
Repository
Commit
Agent
Workflow
Test
Evidence
Outcome
   ↓
能力評価
```

へ移行する。

つまり、**「何年やったか」から「何を作り、何を定義し、何を実行し、何を証明したか」へ**評価軸を移す。

## 8. 無尽知化への接続

仕事を経験して終わるのではなく、仕事を知識へ変換する。

```text
Job
 ↓
Task
 ↓
Experience
 ↓
Repository
 ↓
Evidence
 ↓
Ontology
 ↓
Knowledge
 ↓
Agent
 ↓
New Work
 ↺
```

この循環を「無尽知化」と捉える。

求人は単なる応募先ではなく、仕事を知識へ変換する入口になる。

## 9. 中心命題

以上から、`mushochika` の問題設定は「求人情報を整理すること」に留まらない。

> **仕事をOntologyとして定義し、Intentとして表現し、Agentとして実行し、Vibe Codingによって実装し、Evidenceによって能力と成果を証明する。**

最終的には、

```text
Job
 ↓
Work
 ↓
Knowledge
 ↓
Ontology
 ↓
Agent
 ↓
Work
```

という循環を作ることが目的になる。

## 10. エビデンス

- McKinsey, *The State of AI in 2023: Generative AI's breakout year* — 生成AI等による仕事時間の60〜70%の自動化可能性の推計。
- World Economic Forum, *Future of Jobs Report 2025* — 2030年までの1.7億の新規雇用、9200万の置換、7800万の純増、および約40%のスキル変化。
- GitHub Research, *Quantifying GitHub Copilot's impact on developer productivity and happiness* — 95人の開発者を対象とした実験で、Copilot利用者の課題完了時間55%短縮、完了率78%対70%。
- McKinsey, *Agents, robots, and us: Skill partnerships in the age of AI* — Agentによる仕事活動への影響に関する分析。

数字は予測・実験結果であり、将来の実績を保証するものではない。また「自動化可能な仕事時間」は「消滅する雇用」そのものを意味しない。
